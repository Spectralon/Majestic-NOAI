# Тестовое задание для Majestic RP

## Как устроен проект

1. Вся симуляция на сервере, клиент номинальный (тонкий). Принимает стейт по WS на порте `3443` (конфиг в [StaticDataService](src/infrastructure/services/StaticDataService.ts)) и отрисовывает. На сервер шлёт команды.
2. Первый запуск сервера:

   ```bash
   npm install
   npm run build
   npm run dev
   ```

3. Запуск клиента: открыть [index.html](public/index.html) в любом браузере.
4. Запуск демо - на клиенте нажать кнопку `Start demo`.
5. В процессе демо сервер будет выдавать ошибки на невалидный инпут - смотреть их можно в консоли браузера. Запускайте несколько раз, чтобы увидеть разные сценарии.

## Как устроено демо

Это последовательность команд с клиента с ожиданием результата и задержками для наглядности (хардкод). Управляется только клиентом ([demo.js](public/demo.js)).  
Предметы - разноцветные круги, цвета конфигурируются в [StaticDataService](src/infrastructure/services/StaticDataService.ts). Игрок - тёмно-синий круг, над ним `id`, под ним полоски - `hp`, `armor` и `ammo`. Собранные предметы отрисовываются миниатюрами внутри игрока.

### Сценарий:

1. Спавним двух игроков на случайных позициях в мире.
2. Спавним 3 случайных вида дропа на случайных позициях в мире.
3. Раздаём игрокам 2 цели, они к ним бегут. Третий дроп лежит на земле и со временем исчезает (100 тиков по конфигу).
4. Когда прибежали - подбирают дроп. Скорость игроков и время жизни дропа подобраны так, что игрок может не успеть добежать. В таком случае он попытается подобрать несуществующий дроп, сервер вернёт **ошибку**.
5. Один игрок использует то, что подобрал. Второй - выкидывает обратно на землю. Если на прошлом шаге не успел - игрок всё равно попытается, с сервера получит **ошибку**.
6. Спавним дроп между игроками на равном расстоянии.
7. Игроки бегут к дропу, останавливаются рядом, пытаются подобрать. Удаётся только одному. На попытку второго сервер выдаёт **ошибку**. Здесь также игроки могут не успеть - попытаются, оба получат **ошибку** с сервера.
8. Когда истечёт таймаут - исчезают предметы на земле.

Демо можно (**нужно**) запускать сколько угодно раз, результаты предыдущих запусков не удаляются. Поле не интерактивное - только отрисовка стейта с сервера.  
**Ошибки** можно посмотреть в консоли браузера.

## Архитектура

Общая идея - точка входа со строгим порядком создания и инициализации сервисов. Она же раздаёт им зависимости. DI без DI.

```
src/
├── index.ts                           - точка входа - создание и запуск BootstrapService
├── game/
│   ├── objects/                       - доменные объекты и типы данных
│   │   ├── effects/                   - прототипы эффектов
│   │   ├── items/                     - прототипы предметов инвентаря
│   │   ├── abstract.ts                - интерфейсы
│   │   ├── core.ts                    - базовые типы (как будто бы типы игрового движка)
│   │   ├── EffectInstance.ts          - сущность эффекта в мире
│   │   ├── GroundItem.ts              - сущность предмета в мире
│   │   ├── ItemInstance.ts            - сущность предмета в инвентаре
│   │   ├── Inventory.ts               - инвентарь
│   │   ├── Player.ts                  - игрок
│   │   └── World.ts                   - игровой мир
│   └── services/                      - слой бизнес-логики (application)
│       ├── EffectService.ts           - спавн эффектов
│       ├── EntityMovementService.ts   - перемещение экземпляров сущностей
│       ├── GroundItemService.ts       - операции с предметами в мире (дроп / подбор)
│       └── InventoryService.ts        - операции с инвентарями игроков
├── infrastructure/                    - слой инфраструктуры
│   ├── BootstrapService.ts            - DI-подобная композиция, инициализация и запуск (без FSM, нарушаем SRP)
│   ├── GameFactory.ts                 - фабрика игровых сущностей; она же раздаёт зависимости создаваемым сущностям (нормального DI нет) и регистрирует их
│   ├── GameLoop.ts                    - основной игровой цикл: тикает игровой мир, синхронизирует с БД при спавне / деспавне (по ТЗ); нарушаем SRP
│   └── services/                      - инфраструктурные сервисы
│       ├── StaticDataService.ts       - провайдер статики (конфига)
│       └── GameRegistry.ts            - присваивает id игровым сущностям
├── server/                            - слой I/O
│   ├── GameServer.ts                  - сервер
│   ├── CommandService.ts              - минимально необходимая реализация CLI-подобного инпута; он же раздаёт зависимости командам (нормального DI нет)
│   └── commands/                      - реализации команд под API сервера
├── storage/                           - слой хранения
│   ├── IStorage.ts                    - контракт БД
│   └── RuntimeStorage.ts              - имитация БД
└── utils/                             - утилитарный слой

public/                                - фронтенд
├── app.js
├── core.js
├── render.js
├── demo.js
└── index.html
```

## Проблемы, которые в рамках тестового задания я оставил как есть

1. Некоторые сервисы передаются напрямую, без интерфейсов. Естественно, надо по контракту.
2. [GameLoop](src/infrastructure/GameLoop.ts) сам создаёт себе мир в обход фабрики.
3. Небольшой хак - tick возвращает boolean, деспавним если false. В этом случае не будет синхронизации с БД - реализовано по ТЗ. Как бы сделал я: эмитил события из [World](src/game/objects/World.ts) при спавне / деспавне, подписывался из внешнего сервиса и синхронизировал БД реактивно. По ТЗ - синхронизация прямо внутри операций.
4. В [StaticDataService](src/infrastructure/services/StaticDataService.ts) я объявляю config прям в инициализаторе, JSON конфига нет.
5. По ТЗ я сделал onUse прямо в [IItem](src/game/objects/abstract.ts). Без нормального DI это выстрел в ногу - приходится прокидывать лишние зависимости в прототипы, фабрика распухает. Возникает кольцевая зависимость, приходится делать костыль с прокидыванием зависимостей в [GameFactory](src/infrastructure/GameFactory.ts).init.
6. Можно командой добавить не stackable предмет с любым количеством. Стакаться в любом случае не будет.
7. Клиент реализован на коленке кое-как. Это точно не пример хорошего кода (зато без ИИ).
8. На клиент уходят неинформативные ошибки - просто пакет, который не удалось запроцессить.
9. Над оптимизацией я вообще не работал.
10. Не продуман ресет, не проработана инициализация. initialize есть, cleanup нигде не делал; IInitializable нет. Всё регистрируем, нигде не снимаем с регистрации.
11. Нет единого источника рандома.
